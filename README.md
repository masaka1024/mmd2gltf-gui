MMDのPMXモデル(+VMDモーション)を、可能な限り忠実に **glTF 2.0(.glb)** へ変換するツールです。**GUIとCLIの両方**で使えます。依存は標準ライブラリのみで動作し、テクスチャ変換(BMP/TGA/sph/spa→PNG)にのみPillowを使います。

髪・スカートなどの**物理演算をボーンアニメーションとして焼き込む機能**を搭載。物理エンジンを持たないglTFビューアでも、髪やスカートが自然に揺れた状態で再生できます。

このツールの本来の狙いは、単なるビューア向け変換ではなく、**MMDのデータを他のフォーマット・他の環境へ可能な限り正確に持ち出すこと**です(詳しくは[このツールの狙い](#このツールの狙い)を参照)。

> **▶ すぐ使う(Windows):** [最新版のEXEをダウンロード](https://github.com/masaka1024/mmd2gltf-gui/releases/latest) — Pythonのインストール不要。

## このツールの狙い

mmd2gltfの本来の目的は、**MMDのデータを他のフォーマット・他の環境へ、可能な限り正確に持ち出すこと**です。glTF(.glb)は、そのための「運び出す器(コンテナ)」として使っています。

このため、変換結果は次の**二層構造**になっています。

1. **保存層(`extras.mmd`)** — 剛体・ジョイント・IK設定・付与親・材質のトゥーン/スフィア/エッジ設定など、glTFでは表現できない情報も**生のPMX値のまま完全保存**します。受け取り側(ゲームエンジンや他ツール)は、この層から元のMMDモデルの構造を高い精度で再構築できます。
2. **ベイク層(glTF標準のアニメーション)** — 物理エンジンを持たない一般のglTFビューアでも「そのまま自然に見える」ように、モーションと揺れ物を標準キーフレームに焼き込みます。こちらは近似的なフォールバックという位置づけです。

物理ベイクを使っても保存層は失われないため、「ビューアではベイク済みの揺れをそのまま再生し、エンジンでは生データから本物の物理を再構築する」という使い分けができます。

### 実証: Unityインポーター

この設計が実際に機能することを確かめるため、`extras.mmd` を読み取ってUnity上でモデルを再構築するエディタ拡張を開発しました。以下の動作を複数モデルで確認しています。

- 剛体・ジョイント情報からの**物理(揺れ物)の再構築** — Rigidbody / ConfigurableJoint をボーンに構成し、髪・スカートがUnityの物理エンジンで揺れる状態を復元
- 材質のトゥーン/スフィアマップ/共有トゥーン/輪郭線設定からの**MMD風トゥーン表示の復元**(lilToonベース)

つまり本ツールで変換した .glb は、「ビューアでそのまま見られる」だけでなく、**エンジン側で本物の物理とトゥーン表現を取り戻せるだけの情報**を保持しています。

> インポーター本体は別リポジトリとして公開しています: **[mmd2gltf-unity-physics-importer](https://github.com/masaka1024/mmd2gltf-unity-physics-importer)**(要 UniGLTF / lilToon、URPプロジェクト向け)

## 特徴

- **追加ライブラリ不要** — 標準ライブラリのみで動作(テクスチャ変換時のみ任意でPillow)。
- **PMX 2.0/2.1 を全セクション解析** — メッシュ・スキニング・材質・モーフ・物理設定まで読み込み。
- **VMDモーションをベイク** — ベジェ補間を評価し、MMDと同じ変形順(変形階層→付与→CCD-IK+軸制限)で毎フレーム焼き込み。
- **物理演算のベイク** — 髪・ネクタイ・スカートなどの剛体物理をシミュレートし、ボーンキーフレームとして焼き込み。物理エンジンのないビューアでも揺れ物が動きます。スカートのシルエット調整や貫通対策のオプションも用意しています。
- **IKの扱いを4通りで細かく制御** — フルベイクから「一切解かない」まで([IKの扱い](#ikの扱い)を参照)。
- **glTFで表現できない情報は失わない** — 剛体・ジョイント・IK設定・付与親などを `extras.mmd` に生データで完全保存。物理ベイクを使っても元の物理設定はそのまま残るため、Unity等のエンジン側で本物の物理を再構築することも可能です([Unityインポーター](https://github.com/masaka1024/mmd2gltf-unity-physics-importer)を公開中)。
- **GUI / CLI 両対応** — GUIは日本語/English切り替え、ドラッグ&ドロップ対応。
- **Windows EXE版あり** — Pythonを入れなくても、ダウンロードしてすぐ使えます。

## IKの扱い

VMDモーションを焼き込むとき、IK(足・腕などの逆運動学)をどう処理するかを4通りで選べます。**通常は既定のフルベイクのままでOK**で、意図しない足の動きが出たときに切り替えます。

| モード | 指定 | 挙動 |
| --- | --- | --- |
| **フルベイク(既定)** | `--vmd FILE` のみ | 全IKを解決してアニメーションに焼き込む(30fps)。VMD内のIK ON/OFFキーは尊重する。 |
| **全IKを解かない** | `--no-ik` | ベイク時にIKを一切解かず、生のFKカーブのみを出力する。 |
| **一部だけ無効化** | `--disable-ik 名前` | 名前を含むIKボーンだけ無効化(繰り返し可)。例: `--disable-ik 足` で足/つま先IKだけ切る。 |
| **VMDのIKキーを無視** | `--ignore-vmd-ik` | VMD内のIK ON/OFFキーを無視して解く。フルキー版モーション等で足IKがOFF指定されていると既定では自動で解かないため、それを打ち消したいとき。 |

**選び方の目安**

- ふつうのダンスモーション → 既定(`--vmd` のみ)のままで問題ありません。
- 生のカーブを確認したい・IK解決の結果が気に入らない → `--no-ik`。
- 足だけ/腕だけなど特定のIKを切りたい → `--disable-ik 足` のように部分指定。
- フルキー版などでVMD側のIK OFF指定によって足が正しく追従しない → `--ignore-vmd-ik`。

## 物理ベイク

`--bake-physics` を付けると、MMDの剛体物理(髪・ネクタイ・スカートなどの揺れ物)を簡易物理シミュレーション(PBDばねモデル)で解き、結果を**ボーンのキーフレームとして焼き込み**ます。物理エンジンを持たないglTFビューアでも、揺れ物が自然に動いた状態で再生されます。

> **設計方針:** このベイクは「物理エンジンがない環境向けの、今風でもっともらしい揺れ」を目指した近似です。MMD本体(Bullet物理)の完全再現は目標としていません。忠実な物理が必要な場合は、`extras.mmd` に保存された生の剛体・ジョイント情報を使い、Unity等のエンジン側で再構築してください。

### 基本の使い方

```bash
# 髪だけベイク(既定)
python -m mmd2gltf モデル.pmx --vmd モーション.vmd --bake-physics -o out.glb

# スカートも含めて全部ベイク
python -m mmd2gltf モデル.pmx --vmd モーション.vmd --bake-physics --bake-target all -o out.glb
```

- `--bake-target hair`(既定) — 髪・ネクタイなどチェーン状の揺れ物のみ。
- `--bake-target all` — スカートを含む全ての動的剛体。スカートはリング構造を保つ布ソルバーで処理し、体のコライダー(足・腰など)との衝突判定・貫通防止も行います。

### 揺れの調整

| オプション | 既定 | 効果 |
| --- | --- | --- |
| `--hair-drag F` | 0.85 | 速度の保持率(0〜1)。上げるとふわふわ、下げると硬めに。 |
| `--hair-stiffness F` | 1.5 | 元の形に戻ろうとする力。 |
| `--hair-gravity F` | 0.02 | 重力の強さ。0で初期形状を維持。 |
| `--collision-bounce F` | 0.0 | コライダーに触れて押し出されるときの弾み。0で従来どおり、上げるほど接触時にはずむ動きに。 |
| `--collision-margin F` | 0.0 | 布と体コライダーの間に確保するクリアランス(glTF単位)。スカートのクリアランスは下記の実測ベースの2項目が担うため既定0。**髪・ネクタイ等のチェーンに効くのはこの値だけ**なので、髪が頭に食い込むときはここを0.003前後に。 |
| `--hem-extra-margin F` | 0.0 | スカートの**裾側だけ**に追加するクリアランス。根元(腰側)から裾へ滑らかに補間されるため、腰まわりのシルエットを変えずに裾の食い込みだけを抑えられます。 |

### スカートのシルエット調整

点ベースのソルバー(既定)はスカートを「点の連なり」として扱うため、MMD本体の「板状の剛体がジョイントを軸に回る」挙動と比べると、輪切りの段差が出たり、動きが折り紙のように硬く見えたりすることがあります。以下のオプションはそれぞれの症状に対する対策です。いずれも既定OFFで、指定しない限り従来と同じ結果になります。

| オプション | 既定 | 症状と効果 |
| --- | --- | --- |
| `--segment-aware-collision` | OFF | 衝突の押し出しを、パーティクル単体でなく親子ボーン間の「区間(線分)」に対して解決します。脚を上げたときなどに一段のリングだけ飛び出す「階段状の輪切り」を根本から抑えます(スカートのみ。髪には影響しません)。 |
| `--skirt-bone-twist` | OFF | スカートボーンの実際の回転(ねじれ)を捨てずに出力します。ボーン位置は正しいのにセグメントの中間が膨らんで段に見える現象への対策です。回転値には1フレーム最大60°の安全クランプ済みの値を使います(スカートのみ)。 |
| `--vertical-spread-scale F` | 0.5 | 押し出された移動量の一部を、同じチェーンの上下の隣接リングにも分配します。曲がりが一段に集中して折れて見えるのを防ぎ、脚の角度に沿った滑らかな曲がりに近づけます。**1.0を超えると隣の段が押された段より大きく動き、接触が上下に増幅されて傘状に開く原因になります。0.5〜1.0の範囲で調整してください。** |
| `--rb-size-margin-scale F` | 1.0 | スカート剛体(箱形)の実サイズ(最小辺=パネルの厚み)を追加クリアランスとして取り込みます。MMD本体では剛体の体積が自然な「ふくらみ」を生むのに対し、ボーン位置の衝突判定はパーティクルを大きさゼロの点として扱うため、その差をモデルの実データから補います。MMD本体では箱の**面**で当たるため、箱の中心は常に半厚のぶん離れた位置で止まります。つまり1.0は「作者がモデルに設定した厚みをそのまま使う」設定で、物理的な根拠のある既定値です。 |
| `--lateral-slack-scale F` | 6.0 | 横リング拘束(同じ高さの隣どうしのパネル間)に、PMXジョイントの移動制限(linearLimitMin/Max)から求めた「遊び」を許容します。MMD本体はこの範囲内を自由に動かして端でのみ止めるのに対し、従来は常に距離をぴったり引き戻していたため、フレアスカートが折り紙のように硬く見えることがありました。1.0前後から調整(検証済みモデルでは6.0)。 |

**推奨設定** — 2モデル(IA・ぽんぷ長式初音ミク)で貫通量と開き量を実測しながら追い込んだ組み合わせです。数値オプションの既定値はこの構成に合わせてあるので、CLIでは真偽値のオプションを足すだけで再現できます。

```bash
python -m mmd2gltf モデル.pmx --vmd モーション.vmd --bake-physics --bake-target all \
  --segment-aware-collision --skirt-bone-twist --symmetrize-colliders \
  -o out.glb
```

**GUIは起動時からこの設定が入っています。**「詳細設定」から同じ項目を調整できます。

この構成でのスカートの実測値(メッシュ貫通が起きたサンプルの割合):

| モデル | 腰側 | 中段 | 裾側 |
| --- | --- | --- | --- |
| IA | 0.2% | 0.0% | 12.9% |
| ぽんぷ長式初音ミク | 4.1% | 0.6% | 8.2%(裾は3.3%) |

### メッシュ実測によるクリアランス

スカートは、板状の剛体を数枚つないで布を表現しています。ボーンはその板を代表する位置にあり、ひだの谷にあたる部分のメッシュは、そこよりも内側にあります。物理ベイクはボーン(パーティクル)をコライダーの外へ押し出すため、**計算上は貫通していなくても、内側にある布は脚を突き抜けて見えます**。少ない板で布を表す以上、避けられない差です。

`--drape-depth-scale` は、この落ち込み量をPMXのメッシュから直接測って、クリアランスとして使います。

| オプション | 既定 | 効果 |
| --- | --- | --- |
| `--drape-depth-scale F` | 1.0 | メッシュ実測のドレープ深さをクリアランスに使う。1.0が実測どおり、0で無効。位置ごとの値なので、根元から裾へ自動的に変化します。 |
| `--no-drape-probe` | — | 中間パーティクル補正のサンプル点を内側へ寄せる処理を無効化(比較用)。 |

この差の大きさは、モデルによって、また同じスカートの中でも場所によって大きく変わります。検証したモデルでは腰側0.089に対して裾側0.330(PMX原単位)と**約3.7倍の勾配**がありました。一律のクリアランスでは「腰で過剰・裾で不足」を避けられませんが、実測値ならこの勾配がそのまま反映されます。

ドレープ深さを測れなかった剛体(その骨に紐づく頂点が少ない等)には、`--rb-size-margin-scale` の値(剛体の厚み)が引き続き使われます。

### 左右非対称の補正

コライダーの位置やサイズには、左右でわずかな差が含まれていることがあります。MMD本体(Bullet物理)では剛体が体積として当たるため、この程度の差は表に出ません。一方、本ツールのベイクはボーンを点として扱い、そこへクリアランスを足して形を保っています。**差の大きさがクリアランスと同程度になると、片側だけスカートが押し広げられて見えることがあります**。近似側の都合で表面化する現象です。

検証したモデルでは、太ももで0.046、脚で0.067の差がありました(ボーン自体は完全に対称)。

| オプション | 既定 | 効果 |
| --- | --- | --- |
| `--symmetrize-colliders` | OFF | 「左○○」と「右○○」のコライダー対について、ボーンから見た位置・サイズ・回転を鏡像平均し、**ベイクの入力だけ**を左右対称にします。**`extras.mmd` に書き出す元データは変更しません。** 左右で意図的に形を変えているモデルもあるため、既定はOFFです。 |

### 物理レポート(調査用)

| オプション | 既定 | 効果 |
| --- | --- | --- |
| `--physics-report` | OFF | ベイク後に、スカートの各段について「静止時の半径からどれだけ開いたか」「どのコライダーに一番近いか」「押し出しが何%のフレームで起きたか」「メッシュ貫通の推定発生率と深さ」をログ出力します。 |

挙動がおかしいときの原因切り分け用です。特に開き量のタイムライン(動画を10等分した区間ごとの平均)は、「接触のたびに開いて戻っている」のか「一度開いたまま戻っていない」のかを一目で判別できます。集計のぶん少し遅くなります。

### 押し出しの挙動

| オプション | 既定 | 効果 |
| --- | --- | --- |
| `--collision-velocity-damp F` | 1.0 | 押し出しが生む速度を打ち消す度合い。Verlet積分では位置を動かすと速度も変わるため、1.0で「位置だけ直して速度には触れない」完全非弾性の応答になります。0で従来どおり。 |
| `--margin-rest-clamp` | OFF | 各(パーティクル, コライダー)の組み合わせについて、静止姿勢で実際に空いている距離をクリアランスの上限にします。実測ベースのクリアランスを切り詰めてしまうため既定OFFですが、極端に密着したモデルでの逃げ道として残しています。 |

### 貫通・すり抜け対策

素早いモーションでは、(1)1フレームの移動量が大きすぎて衝突判定を飛び越える(トンネリング)、(2)ボーン(関節点)自体は貫通していなくても関節間のメッシュ面が体を視覚的に横切る、という2種類の突き抜けが起こることがあります。

| オプション | 既定 | 効果 |
| --- | --- | --- |
| `--adaptive-substep-threshold F` | 無効 | (1)への対策。アンカーとコライダーの相対移動量が「最寄りコライダー半径のF倍」を超えたフレームだけ、自動で細分化して計算します。目安は0.5〜0.75。指定しなければ完全に従来どおりです。 |
| `--adaptive-substep-max-n N` | 4 | 1フレームを分割する最大数。 |
| `--adaptive-substep-collider 名前` | 全コライダー | 細分化の判定に使うコライダーを限定(繰り返し可)。脚・膝系だけを指定すると、腕の速い動きには反応しなくなります。 |
| `--midpoint-correction` | OFF | (2)への対策。隣接スカートボーン間のメッシュ区間の中点がコライダー内に入ったとき、両端の実ボーンを押し広げる追加パスです。ボーン単位の衝突では原理的に検知できない「メッシュ面が脚を横切る」見た目を緩和します(実測で貫通の深さ・面積を約60〜75%削減。完全には消えません)。 |
| `--midpoint-correction-iters N` | 2 | 緩和処理の反復回数(6程度まで上げてもコスト増はわずか)。 |
| `--midpoint-correction-margin F` | 0.0 | この補正で確保するクリアランス。 |
| `--midpoint-correction-collider 名前` | 全コライダー | 補正対象コライダーの限定(繰り返し可)。通常は `--adaptive-substep-collider` と同じ名前を指定します。 |
| `--midpoint-correction-samples N` | 1 | 区間内のチェック点数。1=中点のみ。2以上でN個の内部点(2なら1/3・2/3点)を検査し、押し出しを両端ボーンへ比例配分します。押し出し方向は常に水平(重力と直交)です。 |

### 貫通をゼロにできない理由

ベイクの結果は**ボーンのキーフレーム**として書き込まれ、メッシュはスキニングでそれに追従します。つまりこのベイクが制御できるのはボーンの位置であって、頂点ひとつひとつではありません。

スカートは数枚の板状の剛体で布を表しています。ボーンはその板を代表する位置にあり、ひだの谷にあたるメッシュはそれより内側にあります。ボーンをコライダーの外に保っても、内側にある布は脚を横切りえます。`--drape-depth-scale` はこの差をメッシュから実測してクリアランスに反映しますが、差の大きさはポーズによっても変わるため、完全に埋めることはできません。

MMD本体(Bullet物理)でも、板状の剛体で布を表す方式であることは同じで、メッシュ単位の非貫通はどちらも前提としていません。スカートの見え方は、剛体とジョイントの調整によって作り込まれています。

参考として、推奨設定での実測値です(サンプルしたフレームのうち、布の谷がコライダーの内側に入った割合と、その深さ。glTF単位):

| モデル | 腰側 | 中段 | 裾側 | 裾側の平均深さ |
| --- | --- | --- | --- | --- |
| IA | 0.1% | 0.0% | 11.3% | 0.0045 |
| ぽんぷ長式初音ミク | 4.1% | 0.6% | 8.2% | 0.0022 |

上段はほぼ解消でき、残るのは裾です。深さ0.0045は、身長1.6の人型に換算しておよそ4mmにあたります。

**完全な非貫通が必要な場合**は、`extras.mmd` に保存された剛体・ジョイント情報を使い、UnityのClothやUnreal EngineのChaos Clothなど、頂点レベルの布シミュレーションを受け手側で構築してください。ベイク層はあくまで、物理エンジンを持たない環境向けの近似です。

### 実験的: 布アルゴリズムの切替

`--cloth-algorithm` でスカート用のソルバーを切り替えられます。

- `points`(既定) — 従来の点ベースチェーン。上記の全オプションに対応した本線のアルゴリズムです。
- `rigid_chain`(実験的) — 各リングの「向き」を直接シミュレートします(慣性+重力トルク+復元力+PMXジョイントの軸別角度制限)。衝突・サブステップ・中点補正には未対応です。
- `rigid_body`(実験的) — 並進+角速度を持つ剛体チェーンです。関連パラメータは `--rigid-body-*` 系で調整できます。

通常は `points` のままで問題ありません。実験的アルゴリズムの詳細パラメータは `--help` を参照してください。

### 衝突モード(食い込み・傘化への対処)

一部のモデルでは、体内部の剛体設定やモデルの想定外の激しいモーションが原因で、スカートが押し広げられて傘のように開いたり、特定の部位に食い込んだりすることがあります。そのための逃げ道を2方式用意しています。

| モード | 指定 | 挙動 |
| --- | --- | --- |
| **通常(デナイリスト)** | `--force-no-collision 剛体名`(繰り返し可) | 指定した剛体だけを完全非衝突にする。それ以外はPMXの非衝突グループ設定どおり。「この剛体が悪さをしている」と分かっているときに。 |
| **限定(アローリスト)** | `--allowed-collider 剛体名`(繰り返し可) | 指定した剛体**だけ**をコライダーとして扱い、それ以外は最初から存在しないものとする(PMXのグループ設定は無視)。VRM SpringBone / VRChat PhysBonesと同じ考え方。 |

GUIでは「詳細設定」から同じことがもっと簡単にできます:

- **衝突モード** — ラジオボタンで「通常/限定」を切り替え、剛体名をカンマ区切りで入力。
- **剛体名を確認...** — 選択中のPMXを解析し、剛体を「静的(コライダー)/揺れ物」に分けて一覧表示。ダブルクリックで入力欄に追加できます。
- **VRM互換モードにする** — 脚まわりの剛体を自動抽出し、ワンクリックで「限定」モードに設定するプリセット。

PMXのグループ設定(group/noCollisionMask)自体も正しく読み込んで反映します。上記のモードは、その設定では対処しきれない場合の上書き手段です。

> **16bitフィールドの解釈について:** PMXのこのフィールドは「非衝突グループフラグ」という名前ですが、**立っているビットは「そのグループと衝突する」を意味します**(Bulletのcollision filter maskそのもの)。PMXエディタのチェックボックス表示(チェック=非衝突)とは反転しているため、名前のとおりに読むと判定が逆になります。three.jsのmmd-parserは `groupTarget`、sabaは `m_collisionGroup` と、いずれも「非衝突」という語を避けた名前に変えています。本ツールもこの解釈に統一しました(`extras.mmd` に書き出す値はPMXのまま。詳細は `mmd2gltf/physicsGltf_schema.md`)。

### 剛体を目で確かめる(物理インスペクター)

`tools/mmd_physics_inspector.html` は、変換後のGLBをブラウザで開いて中身を確認するためのスタンドアロンツールです(ブラウザにドラッグ&ドロップするだけ。インストール不要)。

`extras.mmd` に保存された剛体・ジョイント・衝突グループを3D表示し、剛体をクリックすると形状・サイズ・モード・紐づくボーン・衝突するグループ・その剛体と衝突する剛体の数を表示します。モデルの調整で迷ったとき、「どの剛体がどこにあるのか」「本当に衝突する設定になっているのか」を数分で確認できます。

## ビュアー互換性の注意

- macOSのQuick Look/プレビュー(RealityKit)はglTFのモーフターゲット自体に非対応です。モーフが「抜ける」のはビュアー側の制限で、ファイルは正常です。
- sparseアクセッサの実装が不完全なビュアー/ローダーではモーフ適用時にメッシュが壊れる(顔が透ける・口パクが別の場所の変形に見える等)ことがあります。その場合は `--morph-mode dense` で変換してください(容量は増加)。**UniGLTF/UniVRM系のUnityインポータで使う場合も `dense` を推奨**します。sparse時もゼロ基底bufferViewを持たせているため、sparse未対応ローダーでは「モーフ無効」に安全に落ちます。
- 動作確認済みの推奨ビュアー: three.js系 (gltf-viewer.donmccurdy.com)、Babylon.js Sandbox (sandbox.babylonjs.com)、Blender 3.x以降のglTFインポータ。

## 変換内容(忠実度)

glTFで直接表現できるもの:

- メッシュ(頂点・法線・UV・材質ごとのプリミティブ分割)
- スキニング(BDEF1/2/4。SDEF/QDEFは線形ブレンド近似+元パラメータを保持)
- ボーン階層(PMXボーン順=skin.joints順なのでインデックス互換)
- 頂点モーフ→モーフターゲット(sparseアクセッサで軽量)、UVモーフ→`TEXCOORD_0`ターゲット、グループモーフ→展開して合成ターゲット
- 材質(拡散色→baseColor、両面フラグ、αによるBLEND判定、テクスチャ埋め込み)
- VMDモーション: ベジェ補間を評価し、MMDと同じ変形順(変形階層→付与→CCD-IK+軸制限)で毎フレームベイク。モーフキーはweightsアニメーションに変換
- 物理(任意・`--bake-physics`): 剛体物理をシミュレートしてボーンの回転+平行移動キーフレームとして焼き込み。PMXの非衝突グループ(group/noCollisionMask)を尊重

glTFに存在しない概念は `extras.mmd`(生のPMX値・MMD左手系座標)として全て保存:

- 剛体・ジョイント(物理)、IK設定、付与親、固定軸/ローカル軸、表示枠
- ボーンモーフ・材質モーフ・フリップ/インパルスモーフの内容
- 材質のスフィアマップ/トゥーン/エッジ/環境光/反射光設定、メモ
- 頂点単位データはカスタム属性として保持: `_ADDUV1..4`、`_EDGESCALE`、`_SDEF_C/_SDEF_R0/_SDEF_R1`、`_WEIGHTTYPE`

座標変換: 位置/法線 `(x,y,z)→(x,y,-z)`、クォータニオン `(x,y,z,w)→(-x,-y,z,w)`、三角形は巻き順反転。

## 制限

- PMD(旧形式)・PMX2.1のソフトボディは未対応(PMXへの変換はPMXEditor等で)
- 物理ベイクは簡易シミュレーションによる近似で、MMD本体(Bullet)の挙動を完全再現するものではありません。衝突判定はボーン(剛体)単位で、メッシュ頂点単位ではないため、素早い動きでは布のメッシュ面が体を視覚的に横切ることがあります(すり抜けは `--adaptive-substep-threshold`、メッシュ面の横切りは `--midpoint-correction` で緩和できますが、完全には消えません)。また、モデルの剛体配置が想定していない極端なモーションでは破綻することがあります(これはMMD本体でも起こりえます)。忠実な物理が必要な場合は `extras.mmd` の生データからエンジン側で再構築してください
- MMDのトゥーンシェーディング/スフィアマップ/エッジ描画はglTFのPBRでは再現不可のため、見た目はビューア依存です(`--unlit`で近づきます)
- 共有トゥーン(toon01〜10.bmp)はMMD本体同梱のため埋め込まれません(番号はextrasに保持)
- VMDのカメラ・照明・セルフ影キーは対象外
